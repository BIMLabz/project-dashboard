Your own tiny harness - part 2

Somewhere in every coding agent there is a moment when the model asks to run a program. Maybe it wants to run the tests. Maybe it wants a quick script that drops a file into the project folder. Either way, a real process is about to start on your machine, and someone has to decide whether that is okay.

Last time we built the core of a tiny harness, the small program wrapped around the model. The model only proposed steps. The harness asked for a yes or no before writing hello.txt, ran the one write tool it owned, kept a text log of every step, and finished by reading the file itself to confirm it held exactly the two letters ok. If you missed it, start here: Build a tiny coding-agent harness from scratch - part 1.

This time we give the harness a second tool, run_command, which starts a program. The rule stays the same as for writes. Ask first, and start the process only after a yes. A no has to mean the process never exists at all, and the program has to stay inside the project folder.

You will learn why handing a model one free-form command line is a weaker safety check than it looks, how to start a program from a plain list of words so nothing gets reinterpreted along the way, how one marker file turns "did it really run?" into a question the folder answers, and how the same byte check from last time still decides when the job is done.

Three words for this part

That yes before a process starts is Allow. That no so the process never starts is Deny. The operating system process the harness would start is the child. If you have never shipped a harness, those three words are the plot of this piece. Everything else is how we keep them honest when the tool is "run a command."

A lot of products take one shell string and call that Allow. A shell is the command interpreter that reads a whole line of text and decides what to run. You check a box on a sentence, and the sentence can still mean pipes, redirection, and a second interpreter you never named. That kind of checkbox is a fake Allow, and it is worth asking why. This repo does something smaller and cooler. The tool takes an argv list (program first, then arguments). Node starts that list with shell: false. Deny means spawn, Node's call for starting a process, is never reached, so there is no child and no half-started log.

The code lives here:

https://github.com/ashishpatill/harness-from-scratch

Clone it when you are ready. The demos below use the same public tree. This slice is the spawn verb, run_command, with the working directory confined and exact-byte proof when Allow wins. The joy is tinkering until Allow and Deny mean what they say.

Why a write tool is not enough

A write tool owns one change on disk. Bytes land at a path. You can refuse the path, refuse the write, and re-read the file after stop to know whether the run told the truth.

Coding work usually needs a second kind of change. Start a process. Capture the exit code and the two output streams, standard output (stdout) and standard error (stderr). Feed that result, which the harness calls an observation, back into the loop. Prove done the same way you already do for a file. Skip that tool and people paste a shell string into the product and call it "the agent ran a command." The fix here is small on purpose. Register one more tool. Keep the same gate, the same journal, and the same proof. You are building a harness you can hold in your head.

Plain verbs before the jargon

Four words show up in the code. Teach them as actions at a whiteboard.

argv is the argument vector. A list of strings. First string is the program. The rest are arguments. Nobody joins them into a shell line. Example shape: [node, "-e", "/* small script */"]. When you pass that list, you mean "start this program with these args," not "hand /bin/sh a poem."

shell: false is how Node starts that list. child_process.spawn gets the file and the args separately. It does not hand a single string to /bin/sh -c. So "echo hi && rm -rf /" as one blob is not a valid tool argument here. A string where an array belongs is rejected before spawn. That rejection is a feature you can love. It makes the fake Allow harder to smuggle in.

cwd is the working directory for that child. It resolves under the workspace root with the same string-prefix escape check used for write paths. Ask for cwd: ".." and the tool throws. The process does not start outside the root because the call never reaches spawn.

Allow is still the yes answer from the gate, the piece of the harness that answers yes or no. Journal the tool request first, meaning write it to the run's log with argv and cwd on disk. Then ask the gate. Only on allow does ToolRegistry, the harness object that holds the tools, call spawn. On deny or timeout (a third pre-set not-allow answer for tests), the loop throws. There is no observation event. There is no child.

Those four verbs are the whole law for this slice.

The spawn the harness owns

ToolRegistry already had write_file. Beside it sits run_command.

{
  name: "run_command",
  description: "Run an argv-only process inside the workspace (no shell string)"
}

Arguments are only { argv: string[]; cwd?: string }. The call path checks argv, confines cwd, then spawns. The surface stays short on purpose, so a shell is harder to invent by accident.

function assertSafeArgv(argv: unknown): asserts argv is string[] {
  if (!Array.isArray(argv) || argv.length === 0) {
    throw new Error("run_command requires non-empty argv array");
  }
  if (!argv.every((part) => typeof part === "string")) {
    throw new Error("run_command argv elements must be strings");
  }
}

function runArgv(argv: string[], cwd: string) {
  return new Promise((resolvePromise, reject) => {
    const child = spawn(argv[0]!, argv.slice(1), {
      cwd,
      shell: false,
      stdio: ["ignore", "pipe", "pipe"]
    });
    // collect stdout/stderr, resolve with exitCode
  });
}

After Allow, the registry does this:

assertSafeArgv(decision.arguments.argv);
const cwd = resolve(root, decision.arguments.cwd ?? ".");
assertInsideWorkspace(root, cwd, "cwd");
const result = await runArgv(decision.arguments.argv, cwd);
return JSON.stringify({
  argv: decision.arguments.argv,
  cwd,
  exitCode: result.exitCode,
  stdout: result.stdout,
  stderr: result.stderr
});

Empty array, bare string, or a number in the list all throw before spawn. cwd that walks out of the workspace throws the same way a write path would. That is ownership. The model proposes argv. The harness decides whether a process exists. If you like building tools, this is the satisfying part. You get a tiny application programming interface (API), the surface other code calls, that refuses to lie.

Scripted guest that proposes run_command

Continuous integration (CI), the robot that re-runs the test suite on every change, needs a guest that never hits the network. FakeModel is that guest, a scripted decide function with fixed modes. Mode run is the one for this tool, standing in for a real model so you can prove the harness offline.

On the first decide call it returns a run_command tool decision. After a tool observation it stops with a short answer. The argv it proposes is Node writing hello.txt (exact bytes ok) and a marker file ran.txt inside the workspace. No shell. No network. Just a child that either ran or did not.

export function runCommandThatWritesHello(): { argv: string[]; cwd?: string } {
  return {
    argv: [
      process.execPath,
      "-e",
      "require('node:fs').writeFileSync('hello.txt','ok'); require('node:fs').writeFileSync('ran.txt','1')"
    ]
  };
}

// inside FakeModel.decide, mode === "run"
if (!messages.some((message) => message.role === "tool")) {
  return { kind: "tool", tool: "run_command", arguments: runCommandThatWritesHello() };
}
return { kind: "stop", answer: "hello.txt contains exactly ok (via run_command)" };

ran.txt is the honesty marker. Sit with that for a second. If Deny works, that file must not exist. If Allow works, it must exist, and hello.txt must still be exact bytes ok. The harness does not trust the stop sentence. It re-reads hello.txt itself. Without the marker you argue about log lines. With it, the filesystem answers.

Allow path you can run

Tests need the same yes/no without a keyboard. FixedGate is a helper that returns a pre-set allow, deny, or timeout when it is created. CI never waits on a person. You bake the answer in, then watch whether the harness respected it.

From the repo root:

node --experimental-strip-types src/cli.ts run-allow

The command-line interface (CLI) wires FakeModel mode run and FixedGate allow. Task text says create hello.txt by running a command. The loop journals the request, allows, spawns, records the observation, then proves bytes. The first time that path goes green on your laptop, it feels like a trick you built yourself.

What you should see on disk after a green run:

  • workspace/hello.txt is the two bytes ok (hex 6f6b, the byte for o and then the byte for k)
  • workspace/ran.txt exists (the child actually ran)
  • transcripts/run-allow.jsonl (the run's log in JSONL, JavaScript Object Notation Lines, which means one small record per line) ends on stop with proof.exactBytes true

The transcript shape, in order:

1. user task 2. model_decision with tool run_command 3. tool_request with argv and cwd (absolute under the workspace) 4. approval allow 5. observation (exitCode, stdout, stderr as JSON text) 6. model_decision stop 7. proof, then stop

The loop journals the tool request before the gate. That order matters for the deny story next, because you want the ask on disk even when the answer is no.

Deny means never starts

Now flip the gate and run the twin demo. Same guest, same argv, different answer.

node --experimental-strip-types src/cli.ts run-deny

FixedGate returns deny. Exit is nonzero. The failure line is approval deny. Peek at the workspace after. That peek is the point.

On disk after deny:

  • no workspace/ran.txt
  • no workspace/hello.txt
  • transcript has tool_request and approval deny
  • no observation event
  • last event is failure

"The model asked to run" and "the process ran" must stay different sentences. The marker file makes the second sentence falsifiable. If ran.txt appears on a deny run, the harness lied about Deny. Challenge yourself when you demo this. Do not trust the failure line alone. Look for the marker. If it is gone, the harness told the truth.

The loop code is the same gate call used for writes:

await event(options.transcript, toolRequest, onEvent);
const gate = await options.gate.check(decision);
await event(options.transcript, { event: "approval", step, result: gate }, onEvent);
if (gate !== "allow") throw new Error(`approval ${gate}`);
const observation = await options.tools.call(decision);

tools.call is where spawn lives. Deny never reaches it. That single if is the whole romance of the design, one branch that chooses process or no process.

What the suite refuses

Tests spawn the CLI the same way a laptop does. Two scenarios lock the demos. A few unit calls lock the rejects. The challenging part, in a good way, is catching places where a "helpful" shell string would sneak back in.

run-allow. Status 0. Bytes ok. ran.txt present. tool_request tool is run_command. proof.exactBytes true. Last event stop.

run-deny. Status nonzero. No ran.txt. No hello.txt. approval deny. No observation. Last event failure.

Direct ToolRegistry calls also reject:

  • cwd: ".." throws cwd escapes workspace
  • argv as a string throws non-empty argv array
  • empty argv throws the same
  • a non-string element throws argv elements must be strings

Those failures happen inside the tool layer. They never become a half-started child with a confusing log. Suite on this tree stays 21/21 green with Fake first.

Done is still bytes

run_command does not invent a new definition of success. The child can write hello.txt. The harness still reads that file on stop. Wrong bytes fail. Missing file fails. Observation JSON with exitCode 0 helps the next decide call. The proof object remains the file on disk.

You can swap how the guest proposes work without rewriting what "done" means. That separation is why owning a harness feels expressive. Fake today, live tomorrow. The byte judge stays yours.

Honest limits

argv-only is not a shell. No pipes-as-shell. No sh -c helper dressed up as safety. If you need a pipeline, express it as a real program in argv or expand the tool list on purpose later. Say that out loud when you demo.

cwd and path confinement are still string-prefix checks, not an operating system sandbox. A binary that ignores cwd and writes elsewhere is outside this teaching boundary. FixedGate still drives run-allow / run-deny so CI never hangs. Interactive human Allow is a later slice on the same gate interface, same journal shape, different who answers yes or no.

What to run

If you do not have the tree yet, clone it. Then exercise the spawn verb yourself. Run allow, run deny, and peek at ran.txt. That build, break, and check loop is the spirit of the repo.

git clone https://github.com/ashishpatill/harness-from-scratch
cd harness-from-scratch
node --experimental-strip-types src/cli.ts run-allow
node --experimental-strip-types src/cli.ts run-deny

Open transcripts/run-allow.jsonl and transcripts/run-deny.jsonl. Confirm ran.txt only exists on allow. Confirm hello.txt is still exact ok when the child was allowed to run. When those two facts line up, you have felt what a harness is for: Allow before spawn, same guest boundary, same byte judge, and one more tool the harness owns.
