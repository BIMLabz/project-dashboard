Memory kinds in a tiny harness - part 5

Before a coding agent writes hello.txt, it jots a note to itself: the file should hold ok. One step later it looks the note up and uses it. That sounds trivial until you ask where the note lives. Does it vanish when the run ends? Does it survive a restart? Could an older note with the same name sneak into the file instead?

Last time we taught the harness, the small program wrapped around the model, to resume. It read its own log, a JSONL file (JavaScript Object Notation Lines, plain text with one small record per line), found the last step that had fully finished, and continued from there without writing hello.txt a second time. It refused to resume a log that had already ended or had stopped mid-step. Catch up here: JSONL resume in a tiny harness - part 4.

This time we give the agent memory, in three separate kinds. Working memory is scratch paper for the current run. Episode memory is a notebook that stays open from one step to the next while the program is running. Durable memory is a small file on disk that a brand-new run can read back. We use one of them to fill hello.txt and prove the other two stayed out of the way.

You will learn why keeping these three lifetimes in separate buckets prevents a whole class of confusing bugs, how to log every remember and recall so you can see which note caused a write, what a fresh run should wipe and what it should keep, and why storing a note never skips the yes or no before a write.

Starting simple: three maps and two verbs

The small runtime wrapped around the model is the harness. It holds three maps. A map here is a simple lookup table: a name goes in, a value comes out. Working is scratch for this run, and a fresh run wipes it. Episode is notes that stay available from step 1 to step 2 in the same process. Durable survives a new process when a JSON file is configured. JSON is JavaScript Object Notation, a text file of keys and values. The same key can sit in all three maps. The values stay different because the maps never share a bucket.

That store is MemoryStore. You put a string with remember. You look it up with recall. Lookup is by kind and by key. You name the map and the key, and you get that string back, or nothing.

The scripted guest with no network call is FakeModel. In memory mode it remembers episode proof-bytes as ok, remembers a working scratch, remembers a different durable value under the same key, recalls the episode value, and then proposes write_file with that recalled string. The harness still asks for Allow before the write runs. Allow means yes, and the write does not start until that yes is recorded. When the guest stops, the harness reads hello.txt itself and checks the bytes.

The code is public:

https://github.com/ashishpatill/harness-from-scratch

Clone it and run npm run memory. Then open transcripts/memory.jsonl and look for remember and recall lines. hello.txt still reads ok. workspace/.memory/durable.json holds the durable value that was not used for the write.

Why the write uses only one of them

The letters w, e, and d in that picture are the unit test. The demo writes ok, and it gets ok from the episode map.

Episode stores proof-bytes as ok. Durable stores proof-bytes as the string durable-not-used-for-write. The write uses the episode recall. Shared storage would have let the durable string land in hello.txt, and the byte check would fail.

Working exists so a temp note does not have to pretend it should outlive the run. Episode exists so step 2 can still see a note from step 1 after the write has already run. Durable exists so a new process can load a JSON file and get the long-lived map back. One pair of verbs, three lifetimes.

Remember and recall are state the guest can use across steps. They are not the write. The yes or no still sits in front of hello.txt. Storing a note does not skip that yes.

What the memory command does

The memory command builds a MemoryStore with a durable file at workspace/.memory/durable.json. It hands that store to FakeModel in memory mode. The yes is baked in by a test helper, FixedGate, so continuous integration (the robot that re-runs the suite, usually shortened to CI) never waits on a keyboard. FixedGate returns the word you gave it when it was created. Here that word is allow.

The task line is: Remember the proof bytes in episode memory, then create hello.txt containing exactly ok.

Step 1 runs before any tool message exists.

this.memory.remember("episode", "proof-bytes", "ok");
this.memory.remember("working", "scratch", "temp-only");
this.memory.remember("durable", "proof-bytes", "durable-not-used-for-write");
const recalled = this.memory.recall("episode", "proof-bytes");
if (!recalled) throw new Error("memory: episode proof-bytes missing after remember");
return {
  kind: "tool",
  tool: "write_file",
  arguments: { path: "hello.txt", content: recalled.value }
};

Three remembers. One recall. The write content is recalled.value, not a literal sitting next to the path. If episode were empty, the guest throws before it ever asks to write.

The harness journals the tool request, records allow, writes hello.txt, and records an observation. An observation is the note that comes back after the tool actually runs. Then step 2 runs.

Step 2 recalls all three kinds and checks the values still match. Episode is still ok. The working scratch is still temp-only, because this is the same process. Durable is still the unused string. Same key, two different values, in episode and in durable. Then the guest stops. The harness reads hello.txt, demands the bytes ok, journals the proof, and journals stop.

If episode had been wiped between steps, step 2 would throw memory: episode note not available across steps. If the durable string had leaked into episode, it would show up where ok belongs.

Three maps in code

src/memory.ts keeps one JavaScript Map per kind.

function emptyBuckets(): Record<MemoryKind, Map<string, string>> {
  return {
    working: new Map(),
    episode: new Map(),
    durable: new Map()
  };
}

remember writes into this.buckets[kind]. recall reads from that same kind only. An unknown kind throws. An empty key throws. The value has to be a string.

remember(kind: MemoryKind, key: string, value: string): MemoryItem {
  this.buckets[kind].set(key, value);
  this.emit({ op: "remember", kind, key, value });
  if (kind === "durable") this.persistDurable();
  return { kind, key, value };
}

recall(kind: MemoryKind, key: string): MemoryItem | undefined {
  const value = this.buckets[kind].get(key);
  const found = value !== undefined;
  this.emit({ op: "recall", kind, key, value, found });
  return found ? { kind, key, value: value! } : undefined;
}

Durable persist writes one JSON object for the whole map. A missing file on load is treated as empty. Any other read error throws. Working and episode never touch that file.

The log shows the note before the decision

The text log is JSONL, one object per line, appended as the run happens. During the guest's decide call, remember and recall emit small events. The harness writes those as memory lines before it writes the model decision. You can see the note that caused the write without guessing it from the tool arguments.

{"event":"user","task":"Remember the proof bytes in episode memory, then create hello.txt containing exactly ok"}
{"event":"memory","step":1,"op":"remember","kind":"episode","key":"proof-bytes","value":"ok"}
{"event":"memory","step":1,"op":"remember","kind":"working","key":"scratch","value":"temp-only"}
{"event":"memory","step":1,"op":"remember","kind":"durable","key":"proof-bytes","value":"durable-not-used-for-write"}
{"event":"memory","step":1,"op":"recall","kind":"episode","key":"proof-bytes","value":"ok","found":true}
{"event":"model_decision","step":1,"decision":{"kind":"tool","tool":"write_file","arguments":{"path":"hello.txt","content":"ok"}}}

Then the tool request, allow, and the observation. Step 2 recalls episode, working, and durable, then stop, then proof with exactBytes true. That flag means hello.txt was re-read and the bytes were ok.

The durable file after the run is one object:

{
  "proof-bytes": "durable-not-used-for-write"
}

A second MemoryStore pointed at the same path, then loadDurable(), recalls that key and finds the string. Working scratch and episode notes from the first instance are gone. Tests lock that with two stores and one file.

A fresh run wipes the short maps

When the loop is given a memory store, it loads durable first. On a fresh run it then clears working and episode.

if (options.memory) {
  options.memory.loadDurable();
  if (!options.resume) options.memory.clearRunScoped();
}

options.resume means continue an existing journal instead of starting clean. This demo leaves it off, so working and episode clear after durable loads. clearRunScoped is two clear calls. Durable is not in that pair.

A test remembers durable keep-me, plus leftover episode and working notes, then runs the ordinary write path. FakeModel in ok mode ignores memory on that path. After stop, durable is still keep-me. The episode note old is gone. The working note old is gone.

Put a this-run note in durable only when the next process should still have it. A preference stored only in episode is gone when the process is.

npm run memory

That records transcripts/memory.jsonl, leaves hello.txt with the bytes ok, and exits 0.

Honest limits

These maps hold strings, looked up by kind and key. There are three kinds. Durable is one optional JSON object. Copying episode notes into durable is left to you. Working and episode live in the process. End the process with no durable path and those two maps are gone.

The guest calls the store directly. Remember is not behind the yes or no check. Allow still owns the write to hello.txt. Done is still the bytes the harness reads.

What to run

Clone the public repo if you do not have it. You need Node 22 or newer. The script turns on the flag that runs TypeScript (JavaScript with type annotations) without a separate compile step.

git clone https://github.com/ashishpatill/harness-from-scratch
cd harness-from-scratch
npm run memory

Open transcripts/memory.jsonl, hello.txt, and workspace/.memory/durable.json.

After that command, hello.txt holds the two letters ok, and those letters came from the episode note named proof-bytes. The durable file holds a different string under that same key, and the write did not use it. Step 2 of the same run still recalls the episode note. A later fresh run clears that note and the scratch. The durable file stays on disk.
