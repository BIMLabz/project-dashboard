Tweet 1

A new paper from the University of Hong Kong and Tencent found that AI coding assistants do far worse when they pick up a task another assistant already worked on and called done.

Same assistant. Same task. Same grading tests.

The only change is the code it starts from.

272 chars

Tweet 2

Quick terms.

Coding assistant = an AI model that reads a code project, edits files and runs commands to finish a task.
Harness = the code around the model: its instructions, its tools, and the order of its steps.
Test = a small program that runs the code and checks the answer.
Hidden test = a test the assistant never sees, used only for grading.
Handoff = one assistant or person stops, and another picks up the same work.
Percentage point = the plain difference between two percentages. 70% to 20% is a drop of 50 points.

Tweet 3

Why test this? Real work gets handed over all the time.

You come back in a new session to something an assistant said was finished. Or one assistant builds on what another one submitted. Test sets for coding assistants almost always start from clean code.

So the authors made leftover code on purpose. Three cheaper open models (from DeepSeek, Qwen and GLM) tried tasks from two public test sets, DeepSWE and Terminal-Bench. They kept only attempts where the model said "done" and the hidden tests still failed. Two people reviewed each one.

That gave 198 leftover starting points from 111 tasks.

Tweet 4

The next assistant gets only the original request and the leftover code.

No note. No history of the earlier attempt. No sign that it failed.

And the leftover code looks finished. On the bigger test set (real code projects), the typical leftover state already passes 98.4% of the hidden tests. About half have only 1 to 3 tests still failing.

Tweet 5

The numbers. Same model, same harness, same task. Clean start vs leftover start, on real code projects:

Gemini-3.8-Flash: 72.2% → 20.0%
GLM-5.3-Flash: 68.9% → 15.4%
GPT-6-Sol: 65.6% → 33.5%
Kimi-K2.8-Preview: 57.8% → 13.0%
Qwen-3.8-Flash: 51.1% → 30.6%

A drop of 20.6 to 53.5 points.

On the second set, tasks done through the command line on a whole machine, the drop is 20.6 to 34.9 points.

Tweet 6

Maybe the leftover tasks were just the hard ones?

They checked. They took only the tasks each assistant solves from clean code. From the leftover code, the same assistant then failed most of them:

Gemini-3.8-Flash: 75.4% failed
GLM-5.3-Flash: 79.0% failed
Qwen-3.8-Flash: 63.4% failed

These are tasks the same assistant solved from clean code.

Tweet 7

So what goes wrong? The assistants do look at the earlier work. Every run checked what had changed. Then they kept working inside it.

Failed runs kept 86% to 99% of the lines the earlier model wrote.

Throwing it all away and starting over was always allowed. No run on the code projects did that.

In 59% to 88% of failed runs, exactly the same hidden tests failed at the end as at the start.

The authors call this acceptance bias: the assistant treats the earlier work as the definition of what is left to do, and stops checking it against the request.

556 chars (over 280)

Tweet 8

The clearest sign is the files the earlier attempt never touched.

Some tasks need a change in a file the earlier model skipped. From clean code, the assistants change those files in 40.5% to 47.9% of runs. From leftover code, in 6.7% to 15.0%.

They open those files in 38% to 64% of runs. They just leave them alone.

Tweet 9

One run shows it plainly.

Gemini-3.8-Flash, on a Go project. The leftover code fails 11 hidden tests. The same assistant passes all 11 when it starts from clean code.

From the leftover code it looked at the changes, ran the project's own tests (all passed), and submitted after 43 steps without changing a single file.

Its last message: "I have implemented the requested encryption package."

The real fix needed a file the earlier model never touched.

Tweet 10

GPT-6-Sol fails differently. In 11 of 30 sampled failed runs, it named what was wrong with the earlier work and tried to fix it. The other assistants did that in at most 2 of 30.

It still dropped 32 points.

Spotting the problem helps. Fixing someone else's half-right code is a second skill.

Tweet 11

This builds on ExecCritic, a paper we covered earlier. Its example: an assistant patches one path, writes a test for that path, sees it pass, and stops. It stopped because the same run wrote both the fix and the test.

SWE-Residual shows the same stop across a handoff. A different model wrote the work, and the next assistant still took passing checks and finished-looking code as done.

It also flips FixedBench (Gloaguen et al.). There, when a bug was already fixed, assistants still changed code in 35% to 65% of cases. Here, when work only looks done, they change too little. Either way they read the state of the code and skip checking it against the request.

Tweet 12

Limits. 198 leftover states, 111 tasks, two test sets. The command-line set covers only 21 tasks. All earlier work came from three open-model families, none from people. The detailed behavior numbers come from the code-project set only.

What I still can't tell: would one line in the instructions, "check the existing work against the request first", close much of the gap? The paper measures the problem and tests no fix.

If your harness resumes old sessions or passes work between assistants: make the next one check the earlier work against the original request before it builds on it. And treat "the project's tests pass" as weak proof.
