Interactive Allow in a tiny harness - part 3

A coding agent is an AI that works on the code in your project. Most of what it does is talk: it reads your request, thinks out loud, and proposes a plan. Then comes one moment that is not talk at all. It wants to change a file on your computer. This part is about that moment, and about who gets the last word.

Two words first, because everything else depends on them. The model is the AI. It reads the conversation and suggests the next step, but it cannot touch your files by itself. The harness is the small, ordinary program wrapped around the model, and the harness can touch your files. Put the two together and you have a coding agent. The model asks. The harness decides.

Inside the harness sits a gate, one checkpoint that every request has to pass before anything happens. In part 1 the gate guarded writing a file, and in part 2 it guarded starting a program. Both times its yes or no was written down before the run began, so the automated tests never had to wait for a person. Today the gate asks you.

The job is the smallest one we could think of. The model asks to use write_file, the harness's tool for creating a file, to make a file named hello.txt with exactly two letters inside: ok. That's the whole job. It is tiny on purpose, so that afterwards you can open the folder and see with your own eyes whether it happened.

So the harness stops and prints one line:

Allow write_file path=hello.txt content="ok"? [y/N]

In plain English: "The model wants to create hello.txt and put ok in it. Should I?" path is where the file goes, content is what goes inside, and the quotes mark the exact text. [y/N] is your menu. Type y (or yes) for yes. Anything else is no, and the capital N means a bare Enter counts as no too. A yes is what this series calls Allow, and a no is Deny. The cursor blinks. Until you answer, nothing touches your disk.

By the end you will know how to swap who answers that question, a test script or you, without changing the rest of the agent. You will see why a bare Enter should mean no, and how to feed in an answer automatically so the same prompt can be tested with no keyboard at all.

The prompt, the yes, and the no

Once you answer, the write either runs or it does not. Open the folder and hello.txt is sitting there with those two bytes, or the file stays absent. Same prompt. Two outcomes. What changes is who answers.

Tests need the same yes or no without a person at the keyboard. You bake the answer into a small helper at the moment you create it. Pass allow, or deny, or timeout. Timeout is a third pre-set word. The helper returns it at once, the write is skipped, and nobody sits there watching a clock. Continuous integration (the robot that re-runs the suite, usually shortened to CI) never waits on a human. That helper is FixedGate: a gate whose answer is pinned when you create it, before the run begins. The laptop path that waits for one typed line is InteractiveGate: a gate that prints the question, reads your keystroke, and turns it into allow or deny. Both can produce allow or deny. Both leave the same kind of line in the text log. The difference is who answered.

The code is public:

https://github.com/ashishpatill/harness-from-scratch

Clone it and run npm run human-allow when you want the keystroke in your hands. Then open transcripts/human-allow.jsonl. That file is a text log with one JavaScript Object Notation object per line (people call the format JSONL). Check whether workspace/hello.txt appeared. This piece stays on that one file write so the scene stays small enough to hold.

Both helpers implement the same small interface. One method, check, looks at the requested tool and returns allow, deny, or timeout. That interface is ApprovalGate. The picture below is the whole swap.

Read the picture from the blue pill at the top. That pill is ApprovalGate.check, the one question both helpers must answer. Under it sit two cards, and both arrows fall into the same document at the bottom, labeled journal event approval. The journal is that text log. Whoever answered, the loop writes one approval line and then obeys it.

Read that as a sketch of the three words you might pin, drawn so the yes, the no, and the third answer are obvious at a glance. In src/gate.ts the constructor takes one string, "allow" or "deny" or "timeout", and returns it immediately. The 30m is paint on the clock. Copy it into a real timer and CI will hang, which is the failure this helper exists to avoid. FixedGate ignores the path and the bytes and hands back the word you pinned. Deny and timeout both fail the run before the write.

The right card is the laptop. An orange machine with a question mark, captioned InteractiveGate and AskFn(y/N). AskFn is just a function that receives the prompt string and returns one line of text. On your machine that line is whatever you type. In a unit test, a small automated check of one piece on its own, it is the next string from a list. The card has no clock because this helper never invents a timeout of its own.

The bottom box is why a builder should care. Both arrows land on the same approval event. Change who answers, and the rest of the loop stays put. The log does not grow a special "human" event. It stores allow or deny, same as a test.

Why bake an answer before the loop

FixedGate is the honest default for a proof you want to re-run forever. You pick the word before the model speaks. When the guest asks to write hello.txt, the gate returns that word and moves on. Deny and timeout scenarios finish on their own, with no prompt left waiting for a person who will never show up.

On a laptop you usually want the other order. You see the path and the two bytes, and only then do you type. The harness waits for that line, writes the result into the log, and skips the write when you say no.

If every demo only pins allow, Allow turns into a constant. The log still says allow. You never practice the keystroke that keeps a bad write off disk. That is a dull harness. The fun version lets you feel the yes, and still prove the no with no one sitting there.

How a typed line becomes allow or deny

Three small pieces live in src/gate.ts.

AskFn takes the prompt and returns one line. Tests hand it a scripted list. The command line hands it a real question over standard input and standard output (the stream you type into, and the stream the prompt is printed on).

InteractiveGate calls AskFn once per tool request. It trims the line and lowercases it. y or yes becomes allow. An empty line, the end of the input, or a lone n all become deny.

scriptedAsk walks a list of answers for unit tests, so the same InteractiveGate class the laptop uses can run with no terminal and no chance of hanging.

export class InteractiveGate implements ApprovalGate {
  private readonly ask: AskFn;
  constructor(ask: AskFn) {
    this.ask = ask;
  }
  async check(decision: ToolDecision): Promise<GateResult> {
    const prompt = `Allow ${describeDecision(decision)}? [y/N] `;
    const line = await this.ask(prompt);
    const answer = line.trim().toLowerCase();
    if (answer === "y" || answer === "yes") return "allow";
    return "deny";
  }
}

describeDecision turns the request into the readable half of that prompt. For this demo the tool is write_file, so you see the path and the content. If the request were a command, the same function would print the program and its argument list instead. One line, so you can answer it.

export function scriptedAsk(answers: string[]): AskFn {
  let index = 0;
  return async (_prompt) => {
    const next = answers[index];
    index += 1;
    return next ?? "n";
  };
}

Unit tests pass scriptedAsk(["y"]) or scriptedAsk(["n"]). If the list runs out, the function returns n, which the gate treats as deny. A short list cannot accidentally allow a later write.

One ask for a terminal and for a pipe

export function createReadlineAsk(
  input: Readable = process.stdin,
  output: Writable = process.stdout
): AskFn {
  return (prompt) =>
    new Promise((resolve) => {
      const rl = createInterface({
        input,
        output,
        terminal: Boolean((input as NodeJS.ReadStream).isTTY)
      });
      let settled = false;
      const finish = (answer: string) => {
        if (settled) return;
        settled = true;
        rl.close();
        resolve(answer);
      };
      rl.once("close", () => finish("n"));
      rl.question(prompt, (answer) => finish(answer));
    });
}

On a real terminal you see the prompt and you type. Node exposes that with isTTY (TTY is the old teletype name for "a terminal is attached"). In CI, standard input is a pipe, not a terminal. printf 'y\n' | … human-allow feeds the same AskFn. Close the stream without an answer and the close handler resolves "n", which becomes deny. The proof never blocks waiting for a person who is not there.

The settled flag matters more than it looks. The question callback and the close event can both fire. Without the flag you would resolve twice, and the second answer could overwrite the first. First line wins. Then the readline interface, Node's built-in helper for reading one line at a time, closes.

Row 3 is tool_request. The path and the content are already on disk in the log, and the file hello.txt still does not exist. That order is the point. The loop does not care who typed

The agent loop does not special-case InteractiveGate. The order stays the same whoever sits behind check.

The user task is written first. The model asks for write_file on hello.txt. The tool request is appended (path and content in the log, still before the gate). Then approval, with result allow or deny. On allow, the tool runs, an observation is appended, and a later step stops after the exact-byte proof. On deny, the loop throws, a failure line is appended, and there is no observation and no hello.txt.

The core check is short.

await event(options.transcript, toolRequest, onEvent);
const gate = await options.gate.check(decision);
await event(options.transcript, { event: "approval", step, result: gate }, onEvent);
if (gate !== "allow") throw new Error(`approval ${gate}`);
const observation = await options.tools.call(decision);

event appends one line to the text log. tools.call is where the write runs. Deny never reaches it. A human n and a FixedGate constructed with "deny" fail the same way. The thrown message is approval deny. Timeout stays a FixedGate result, approval timeout, and InteractiveGate does not grow a wall-clock of its own.

The same check can sit in front of starting a process. This piece stays on the file write so you can watch one keystroke without a second plot.

Deny from a keystroke

Pass scriptedAsk(["n"]) into InteractiveGate in a unit test. The run throws approval deny. hello.txt is absent. The transcript has the tool request, approval deny, and failure. No observation.

Pipe n into human-allow the same way when you want to see the refuse on the command line. Empty Enter also denies. The prompt shows [y/N] with a capital N because the default is no. A slipped finger should not create the file.

The law stays one sentence. If the gate did not return allow, the write does not run.

What the suite locks

Three proofs sit beside the FixedGate scenarios. They lock the typed path so a later edit cannot quietly skip the question.

InteractiveGate with scriptedAsk(["y"]) writes the bytes ok, records approval allow, keeps the observation, and ends on stop.

InteractiveGate with scriptedAsk(["n"]) leaves hello.txt absent, records approval deny, skips the observation, and ends on failure with the error approval deny.

The human-allow command with a piped y exits 0. transcripts/human-allow.jsonl has approval allow, a proof line with exactBytes true, and stop as the last event. Standard input is not a terminal. CI can re-run that pipe forever.

Automated allow and deny keep FixedGate so the suite stays green without waiting for a person. Interactive only swaps the helper. The loop you already read stays the loop.

When to use which

Use FixedGate when the answer must be known before the process starts. That covers tests, proof scripts, and a deny or a timeout with no keyboard in the room. The baked word is the consent, and the machine never waits.

Use InteractiveGate when a human should see the request and answer once. Local demos. Teaching what Allow feels like. Recording transcripts/human-allow.jsonl with a real y or N, or with a pipe that stands in for one. The keystroke is the consent. The log still stores only allow or deny.

Keep both. Drop FixedGate and CI hangs on a prompt, or flakes when standard input is empty. Pin allow, run a live model, and call that interactive, and the log still says allow while no person typed. Separate transcript names keep that honest. human-allow.jsonl means this path. A file named allow.jsonl means the answer was pinned.

841 chars

Honest limits

InteractiveGate is one line of text. A review screen, a countdown, and a saved "always allow this path" are later work.

createReadlineAsk is a readline over standard input and standard output. It is enough for a terminal prompt and a piped answer. Product chrome around the terminal stays out on purpose.

This demo does not widen the tool list. The write stays inside the workspace folder. The gate answers yes or no. A tighter cage around the process stays outside this slice.

What to run

Clone the public repo if you do not have it.

git clone https://github.com/ashishpatill/harness-from-scratch
cd harness-from-scratch
npm run human-allow

You need Node 22 or newer. The script turns on the flag that runs TypeScript (JavaScript with type annotations) without a separate compile step. Type y once. Open transcripts/human-allow.jsonl. Confirm the approval line says allow, and the proof line says exactBytes true. Then open workspace/hello.txt and check the two bytes.

Then prove CI can record the same shape without a terminal.

printf 'y\n' | node --experimental-strip-types src/cli.ts human-allow

Optionally deny on purpose:

printf 'n\n' | node --experimental-strip-types src/cli.ts human-allow

The exit status is nonzero. hello.txt is missing. The transcript ends on failure, and the approval line says deny.

Type y and hello.txt is on disk, holding the two letters ok. The log records allow, and the proof line says those bytes match. Type n, or press Enter, and the file is never created. The log records deny, and the run stops before any write.

That is the promise. The model can ask for the file. It cannot create it until something answers yes. A test can bake that answer in before the run starts. On your laptop, the yes is the key you just pressed.
