JSONL resume in a tiny harness - part 4

Your laptop battery dies in the middle of an agent run. When you plug back in, hello.txt is already in the folder, holding the two letters ok, and the log of the run simply stops. The write happened. The run never got to say it was finished. So do you start over and write the file again, or pick up exactly where it left off?

Last time we let a person answer the yes or no. Before hello.txt was written, the harness (the small program wrapped around the model) printed a one-line question and waited for you to type y or n. The series calls that yes Allow and that no Deny. Automated tests kept a pre-set answer so they never stalled. Catch up here: Interactive Allow in a tiny harness - part 3.

This time we teach the harness to resume. The log it writes is a JSONL file, short for JavaScript Object Notation Lines, which is plain text with one small record per line. Resume reads that log, rebuilds the conversation up to the last step that fully finished, and keeps going from there. It must never write the file a second time, and it must refuse when the log says the job already ended or when it stopped in the middle of a step.

You will learn what a safe checkpoint looks like in a step-by-step log, how to rebuild the model's view of the conversation from that log, why refusing is the right answer when the log is ambiguous, and how the refusal messages themselves become rules you can test.

Starting simple: the log and the checkpoint

The small runtime wrapped around the model is the harness. Each line of its log is one record of something that happened. Resume means read that file, rebuild the conversation from the last line that records what the tool returned, and keep stepping. Append to the same file. Leave the earlier lines in place. Do not call the write again for a step that already recorded a result. That returned note is an observation.

If the last line is already stop, or already failure, resume refuses and leaves the file alone. If the last line is only the request to write, or a yes with no observation yet, resume refuses too. A cut in the middle of a step must not fire a write that was allowed once and never finished recording.

Why a fresh demo wipes

Most teaching scenarios delete the transcript at the start of a run. Fresh file, fresh story. You can re-run an allow or a deny without hunting old lines.

Resume flips that default on purpose. You pass resume: true. The harness keeps the existing JSONL, reads every line, and continues. Wipe stays the default so the first demos stay easy to repeat. Resume is the verb you opt into when a journal already holds a completed observation and the loop never reached stop.

A journal that ends on observation is the checkpoint you can trust. The tool ran. The result is in the log. The model can be shown that tool message again. A request with no observation, or an allow with no observation, is not a safe place to continue. The harness fails closed there. Fail closed means it refuses, and the file stays as it was, instead of inventing the missing line.

The interrupted fixture

The demo starts from a fixed seed, not from a laptop that crashed. The file test/fixtures/interrupted-after-observation.jsonl has five lines. A fixture is a saved input file that tests reuse, so every run starts from the same place. The command rewrites a path placeholder to your workspace root when it runs.

{"event":"user","task":"Create hello.txt containing exactly ok"}
{"event":"model_decision","step":1,"decision":{"kind":"tool","tool":"write_file","arguments":{"path":"hello.txt","content":"ok"}}}
{"event":"tool_request","step":1,"tool":"write_file","path":"…/hello.txt","content":"ok"}
{"event":"approval","step":1,"result":"allow"}
{"event":"observation","step":1,"content":"{\"path\":\"…/hello.txt\",\"content\":\"ok\"}"}

The user asked for hello.txt containing exactly ok. The model chose write_file. The request was recorded, with the path and the content, before anyone said yes. Approval recorded allow. Allow means the yes happened before the write ran. The observation recorded what the tool returned. There is no proof line and no stop. That gap is the scene resume is built for.

You are continuing after the write, not pretending it never happened.

The command copies that fixture into transcripts/resume.jsonl, writes hello.txt with the bytes ok so the final check can pass without a second write, then starts the loop with resume set.

The seed puts the file on disk so the stop-time byte check can succeed the same way a full allow run would. The journal still carries the observation that says the tool already returned.

Reconstruct, then refuse

The function that rebuilds loop state is reconstructForResume in src/harness.ts.

export function reconstructForResume(events: JournalEvent[]): {
  task: string;
  messages: Message[];
  nextStep: number;
} {
  if (events.length === 0) throw new Error("resume refused: empty transcript");

  const last = events[events.length - 1]!;
  if (last.event === "stop" || last.event === "failure") {
    throw new Error(`resume refused: transcript already terminal (${last.event})`);
  }

  let end = events.length - 1;
  while (end >= 0 && events[end]!.event === "resume") end -= 1;
  if (end < 0) throw new Error("resume refused: no successful observation to continue after");

  const checkpoint = events[end]!;
  if (checkpoint.event !== "observation") {
    throw new Error(
      `resume refused: continue only after a successful observation (last event: ${checkpoint.event})`
    );
  }
  // … rebuild user task + tool messages from every observation …
}

An empty journal refuses, because there is nothing to continue. A last line of stop or failure refuses, because terminal means finished and the transcript stays unchanged. After any trailing resume markers are skipped, the checkpoint has to be an observation. A tool request or an approval refuses. Those are the three rules. The picture draws them as three columns.

When the checkpoint is an observation, the harness rebuilds messages as the original user task plus every observation turned into a tool message. Step numbers continue from one past the highest step already in the log. Then it appends one line:

{"event":"resume","fromStep":2,"observationCount":1,"task":"Create hello.txt containing exactly ok"}

That resume event is a marker, not a second write. The loop in the function skips trailing resume markers when it looks for the checkpoint, so a continue that died right after writing the marker does not get stuck on the marker itself.

What the guest does after the marker

FakeModel is a scripted guest with no network call. In the default ok mode it stops once a tool message is already in the conversation. Resume rebuilds that tool message from the observation, so the next step is stop, not another write_file.

The harness then does the same byte check it does on every clean stop. It reads hello.txt itself and demands the two letters ok. It journals a proof line with exactBytes true, then stop. exactBytes true means the bytes on disk matched. The harness did not trust the model to say the write worked.

A successful transcripts/resume.jsonl has this shape. The lines through observation come from the fixture. Then the resume line, with fromStep and observationCount. Then a model decision whose kind is stop. Then proof. Then stop.

After the resume line there is no new tool_request. That absence is the check. Resume continued. It did not ask for a write that already left an observation.

Tests lock three stories. A fresh allow still wipes the transcript and still works. Resume from an observation reaches stop and proof, with no tool request after the resume line. Resume of a transcript that already ends in stop or failure throws, and the journal is not modified. A unit check also throws when the last event is allow without an observation.

The error strings are the policy

When resume throws, the message is the rule you can read out loud.

resume refused: empty transcript means there was nothing to continue.

resume refused: transcript already terminal (stop) means the job already finished.

resume refused: transcript already terminal (failure) means the run already ended in a deny, a timeout, or another hard error. Deny means the write never started. Timeout is a pre-set third answer some tests return so a suite does not wait on a person.

resume refused: continue only after a successful observation means you are looking at a cut in the middle of a step.

Those strings are what the tests assert. A resume that rewrote a finished transcript would be a silent lie. A resume that fired the write again after an allow with no observation would duplicate the file.

799 chars

Honest limits

This command does not recover a tool call that died halfway. If the process died between the allow and the observation, the answer is refuse, rather than a guess at the missing line. A multi-day session, and notes that outlive the run, stay outside this command. It continues after one completed observation line in a JSONL journal.

Default demos still wipe. The opt-in path stays strict.

What to run

Clone the public repo if you do not have it. You need Node 22 or newer. The script turns on the flag that runs TypeScript (JavaScript with type annotations) without a separate compile step.

git clone https://github.com/ashishpatill/harness-from-scratch
cd harness-from-scratch
npm run resume

Open transcripts/resume.jsonl and hello.txt.

After that command, the journal still has the observation from the seed, then a resume line, then stop. Nothing after the resume line asks to write hello.txt again. The file still holds the two letters ok, because the write had already landed before you continued.

You picked up a job that had finished the write and had not yet said stop. The log grew. The file was not written twice.
