Build a tiny coding-agent harness from scratch - part 1

Ask a coding agent to create a file called hello.txt with the two letters ok inside, and it will usually tell you, cheerfully, that it did. Then you open the folder. Sometimes the file is there. Sometimes it holds the wrong text. Sometimes it never existed, and the only thing that happened was a confident sentence.

That gap between what a model says and what is on disk is where this series lives. A coding agent is really two pieces. The model reads the conversation and proposes the next step. The harness is the small program wrapped around it, the part that decides whether a step may happen, runs the tool, writes down what happened, and checks the result itself.

Over seven short parts we build that harness from scratch, one ability at a time, in a public repo you can clone, run, and break on purpose:

https://github.com/ashishpatill/harness-from-scratch

Every part proves itself with the same tiny job, create hello.txt holding exactly ok, so you always know what success looks like.

This first part builds the core loop. The model is treated as a guest. It can ask for things, and the harness owns everything that matters: the yes or no before any file is written, the short list of tools the model may use, the text log of every step, and the final check that reads hello.txt byte by byte.

You will learn why a yes or no before a write works best as plain data the loop can test, how a scripted fake model lets you exercise the whole loop with no network and no paid key, why "done" should mean a file you read yourself rather than a sentence you were told, and how to plug in a real model later without rewriting any of the rules.

Two pieces, one boundary

People argue about models. The bill and the failure modes usually come from the harness.

The model proposes the next step. The harness asks for a yes or no before any write to disk or any program start. This series calls that yes Allow and that no Deny. The harness runs only the tool that was allowed. It feeds the tool's result back to the model, and that result is called an observation. Then it decides what "done" means by checking something outside the model's mouth.

The model is a guest. It returns a decision. It never writes the disk. It never gets to declare the run a success. The harness owns truth.

Most people meet the agent as a product. Claude Code. Cursor. Codex. Those products are good. They also hide the boundary. You do not see the yes or no before a write. You do not get to swap what "done" means. You do not hold a log and a file you checked yourself.

So I built a tiny teaching harness and put it on GitHub. It runs on Node 22 with zero package dependencies. The first guest is FakeModel, a scripted stand-in for a real model that needs no network and no key. A real model can plug into the same spot later. Every run writes a transcript, a text log in a format called JSONL (JavaScript Object Notation Lines). JSON is the plain-text format of keys and values most web services speak, and JSONL simply means one small JSON record per line.

What you own when you own the loop:

  • Which model sits behind the same socket
  • Which tools exist, and how short that list stays
  • When a change is allowed (deny means the write, or the program start, never runs)
  • How "done" is proven (a sentence is prose, a file you read is proof)
  • What gets written into a log you can open after the process exits

Once those verbs are yours, you can change the guest without rewriting the law of the loop.

Why a tiny public tree

Most "build a coding agent" posts jump to a vendor software development kit (SDK) and a paid key. Then every loop bug is also a web request bug. Or they clone a big agent and narrate a tour. You leave with vocabulary. You do not leave with a gate you can deny.

I wanted the opposite order. Prove the law with FakeModel. No network. No key. Then optionally put a live guest on the same path. If live fails, you know it failed as a guest, not as a missing harness.

Taste choice: Node 22 with --experimental-strip-types, a flag that lets Node run TypeScript files directly. No compiler. No node_modules. Built-in test runner and fetch. If the demo needs a package manager before it needs a gate, the lesson already leaked.

Clone it, run the proof, then keep reading:

git clone https://github.com/ashishpatill/harness-from-scratch
cd harness-from-scratch
./run-proof.sh

Success means tests pass, hello.txt is exactly the two bytes ok (hex 6f6b, the byte for o and then the byte for k), and transcripts/allow.jsonl ends on stop with exactBytes true.

Contracts first

Everything hangs off a few types. Decisions are tool requests or a stop. The model only decides. The gate, the piece that answers the yes or no, only answers allow, deny, or timeout. Timeout is a third not-allow answer that tests can pin.

export interface Model {
  decide(messages: Message[], tools: ToolSpec[]): Promise<Decision>;
}

export type GateResult = "allow" | "deny" | "timeout";
export interface ApprovalGate {
  check(decision: ToolDecision): Promise<GateResult>;
}

FakeModel and the live client both implement Model. FixedGate (a gate with its answer baked in) and InteractiveGate (a gate that asks a person) both implement ApprovalGate. The loop never imports a provider SDK. It imports contracts.

Tools stay short on purpose. The registry ships write_file and argv-only run_command. Argv is the program name plus its arguments, passed as a list, with no shell in between. A shell is the command interpreter that reads a whole line like ls | grep x. The model cannot invent a shell string tool that does not exist.

Allow is a return value

Products turn consent into UI chrome. In this harness, Allow is data.

export class FixedGate implements ApprovalGate {
  private readonly result: GateResult;
  constructor(result: GateResult) {
    this.result = result;
  }
  async check(_decision: ToolDecision): Promise<GateResult> {
    return this.result;
  }
}

FixedGate looks almost insulting. That is the point for continuous integration (CI), the robot that re-runs the tests on every change. You pin allow, deny, or timeout. Deny means the write never runs. Timeout means the same. Tests never hang waiting for a human.

Interactive Allow is also on the tree. InteractiveGate asks y/N, at a terminal or with the answer piped in. Same journal shape. Automated scenarios keep FixedGate so CI stays green. Run npm run human-allow when you want a keystroke on disk.

If you skip this layer, "the model decided to write" and "the file appeared" become the same sentence. They are not.

The loop that owns truth

runAgent, the function that runs the loop, is the law. Ask the model. Log the decision. On stop, read hello.txt yourself. On tool, ask Allow, then call the tool, then push the observation back.

const decision = await options.model.decide(messages, options.tools.specs);
if (decision.kind === "stop") {
  const bytes = await readFile(resolve(options.workspace, "hello.txt"));
  if (!bytes.equals(Buffer.from("ok"))) {
    throw new Error("missing proof: hello.txt bytes are not exactly 'ok'");
  }
  return decision.answer;
}
const gate = await options.gate.check(decision);
if (gate !== "allow") throw new Error(`approval ${gate}`);
const observation = await options.tools.call(decision);
messages.push({ role: "tool", content: observation });

The transcript is a text log, one JSON object per line. You can open it after the process exits. That is how you debug without trusting console vibes.

The proof is exact bytes. Hex 6f6b is ok. Wrong content fails. Missing file fails. The model's stop answer is prose. Prose does not pass.

maxSteps, a cap on how many steps one run may take, bounds a guest that never stops. Loop mode in FakeModel hits that wall on purpose.

FakeModel first, then a live guest

FakeModel is a scripted actor. Modes cover ok, error, loop, run, memory. No network. No key.

ok writes once, then stops after a tool observation. error throws before any tool. loop keeps requesting writes so maxSteps can fail the run.

export class FakeModel implements Model {
  async decide(messages: Message[], _tools: ToolSpec[]): Promise<Decision> {
    if (this.mode === "error") throw new Error("deterministic model failure");
    // ok / loop path (run and memory modes live beside this in the same file)
    if (this.mode === "loop" || !messages.some((message) => message.role === "tool")) {
      return { kind: "tool", tool: "write_file", arguments: { path: "hello.txt", content: "ok" } };
    }
    return { kind: "stop", answer: "hello.txt contains exactly ok" };
  }
}

That suite is why Fake comes first. You can lock deny, timeout, missing proof, model error, and non-stop without spending a token. When those are green, the harness law is real.

Then the live guest plugs into the same Model socket. OpenAI-compatible means any service that accepts requests in the same shape as OpenAI's chat service. You set OPENAI_API_KEY or OPENROUTER_API_KEY, where an application programming interface (API) key is the secret a provider gives you so your program can call its service. OPENAI_BASE_URL is the origin only (no /v1). No key means live skips cleanly. CI stays Fake-first.

if (scenario === "live") {
  const client = clientFromEnv();
  if (!client) {
    console.log("live skipped: OPENAI_API_KEY (or OPENROUTER_API_KEY) not set");
    process.exit(0);
  }
  model = client;
} else {
  model = new FakeModel(modelMode);
}

Same runAgent. Same tools. Same byte check. Live is a guest swap, not a second product.

Live with a key and FixedGate on allow is still not the same path as interactive Allow on a laptop. Keep those runs separate so the article stays honest.

Tools, confined

ToolRegistry, the harness object that holds the tools, exposes two specs and one call path. Path and working directory (cwd) confinement are string checks, not an operating system sandbox. Still enough to refuse escapes outside the workspace root.

async call(decision: ToolDecision): Promise<string> {
  const root = resolve(this.workspace);
  if (decision.tool === "write_file") {
    const target = resolve(root, decision.arguments.path);
    assertInsideWorkspace(root, target, "path");
    if (this.actuallyWrite) {
      await mkdir(dirname(target), { recursive: true });
      await writeFile(target, Buffer.from(decision.arguments.content, "utf8"));
    }
    return JSON.stringify({ path: target, content: decision.arguments.content });
  }
  // run_command: argv-only spawn, cwd confined the same way
}

The actuallyWrite flag exists for a missing-proof scenario. The model can believe it wrote. The harness can refuse to touch disk. Then the byte proof fails on purpose. That is how you teach "observation is not proof."

Scenarios the suite actually fails

The command-line interface (CLI) is the human entry. Tests spawn it so CI and a laptop see the same path.

Scenarios you can name out loud:

  • allow. FakeModel writes, gate allows, bytes are ok
  • deny / timeout. Gate refuses, file never appears
  • missing-proof. Tool call is lied about, disk stays empty, proof fails
  • model-error. Guest throws before a tool
  • non-stop. Guest never returns stop, maxSteps kills the run
  • live. OpenAI-compatible guest if a key exists, otherwise skip cleanly

That list is the proficiency check. If deny does not leave the workspace empty, you do not have Allow. If missing-proof still exits 0 because the model said "done", you do not have proof. If live is required for CI green, you do not have a Fake-first harness.

Independent proof also re-reads hello.txt and the transcript from outside the harness process after the Allow scenario. Same stack. Second opinion. That is how you stop the agent from grading its own homework.

What else is already on the same repo

Nine TypeScript modules plus tests form the core. Shared contracts. FixedGate. ToolRegistry. FakeModel. OpenAI-compatible live client. runAgent. CLI scenarios. Tests that spawn the CLI so a laptop and CI see the same path.

The public tree is not a Part 1 stub. After the core loop landed, these slices were built and tested on the same harness:

  • Safe run_command. argv array only, shell: false, cwd confined. Deny means the process never starts.
  • Interactive Allow. human y/N with the same approval journal events FixedGate writes.
  • JSONL resume. continue after the last successful observation; refuse to resume a finished stop/failure.
  • Memory kinds. working / episode / durable maps, journaled remember/recall. Simple keyed notes for teaching, without retrieval-augmented generation (RAG, which searches a document store).
  • Basic TUI. A text user interface (TUI) that reprints each journal event to the terminal as a tagged line.

Demos: npm run human-allow, npm run resume, npm run memory, npm run tui, plus run-allow / run-deny for the command tool. Full walkthrough lives in the repo README and docs/articles/part-1.md.

Why this is harness engineering

Leaderboards love model names. Same model, three harnesses, and pass rates often sit in the noise while tokens per solved task jump by tens of times. Public harness comparisons often show failure fingerprints that stick to the shell across models: early stops, verify loops, wall-time burn. The model name on the chart did not carry that story.

If you only print the model, you are ranking the wrong object.

That is why Part 1 stays on the tiny loop and the public repo. Own Allow, own the tool list, own the byte check, then invite a live guest on the same socket. Everything else in the tree is the same law, one verb at a time. Clone it, deny a write, break the bytes on purpose, and watch the harness refuse to lie for the model. That is the whole lesson in plain sight.

Harness engineering is the craft of owning that object. Consent before mutation. Short tool lists. Observations that are real tool returns. Done as something you verify. Logs you can open after exit. Guests you can swap without rewriting the law.

Building a tiny harness from scratch is how you feel those verbs in your hands. The repo is public so you can run the same proofs:

https://github.com/ashishpatill/harness-from-scratch

Honest limits

This is a teaching harness. Path and cwd confinement are string-prefix checks, not an operating system sandbox. Argv-only command is not a shell. Memory is keyed maps, not embeddings. The TUI reprints the journal and uses no terminal screen library. Streaming, retries, concurrency, and token accounting stay out on purpose.

If a product already does everything you need, use the product. If you care about cost, consent, and what "done" means, own a harness. Start tiny. Keep the guest swappable. Make the file on disk the judge.
